# BEETLE V1.9: Firmware switching, dual-flash and recovery

## Scope

BEETLE's running application receives firmware update requests over USB-MIDI. It first checks the package, stores a loader in dedicated SPI NOR staging, and asks the chip's SPL to run that loader. This is a **single-bank update**. No automatic A/B rollback is available.

## Confirmed source-level causes in 1.8.3

1. A failed first JEDEC probe could be permanently cached as unsupported, preventing future OTA writes for that boot. V1.9 refreshes the chip identification before an explicit OTA attempt, with audio paused.
2. An unknown pre-existing marker in `0xE0000..0xE4FFF` prevented all ordinary community OTA attempts, even if the incoming package passed all integrity checks. V1.9 reclaims that **BEETLE-reserved OTA** region only after the incoming package and chip have passed preflight. Former firmware's data in that region can be overwritten.
3. `ota_host_app_compatible()` required the exact size of BEETLE's original app slot, excluding some FM1 app-only packages. V1.9 accepts variable lengths **within the old 0x93000 app-only boundary**, with complete CRC verification.
4. The update handoff record always named `ota-FM-1_015`, but the rebuilt V1.8.3 Felucca-lineage loader was `ota-FM-1_2123`. V1.9 uses the conventional `ota-FM-1_900` for Felucca-like loaders and preserves `ota-FM-1_015` for the byte-pinned stock V15 loader. This is a protocol-compatibility correction, not hardware proof.
5. The built-in app-only loader writes `0x4000..0x92FFF`. Stock **V16** extends through **0xA8FFF**, carries another boot header and requires a whole-image installation through a compatible external ROM/UBOOT tool. V1.9 refuses it before staging.

## Supported switching paths

| Destination | V1.9 route | Limitation |
|---|---|---|
| App-only Felucca-family package, compatible verified loader | USB-MIDI / Firmware Hub, tested in host replay | Actual hardware, USB reconnect, target firmware's flash support still require validation |
| Original M-VAVE stock **V15** | Exact SHA-256-pinned V15 image and loader; native host replay uses a synthetic shape unless a genuine V15 fixture is provided | Real-file hardware transition not verified |
| Original M-VAVE stock **V16** | External **mask-ROM/UBOOT full-restore**, not BEETLE's app-only OTA | Different boothead and firmware extent; a backup is essential |
| Unknown loader or incompatible flash / app region | Refuse safely | Use verified ROM/UBOOT tools instead of suppressing checks |
| Firmware that does not support UC25HQ80 | Do **not** install on new-chip FM1 | BEETLE cannot retrofit another firmware's flash driver |

## Identify hardware

The old flashchip is Puya P25Q80, JEDEC `0x856014`. The newer is UCUN UC25HQ80, JEDEC `0xB36014`. Both are 1 MiB SPI NOR, but firmware must recognize the correct ID for its own writes. Use an external read-only device inspection via M-Flasher's ROM download mode to identify it. There is no reliable external-case marking documented.

## If V1.8.3 is stuck

Before experimenting, export all twelve BEETLE projects and save the U01–U13 `.beetlebank`, plus an independent full flash backup if possible. Try The Firmware Hub **Rescue**: https://thefirmwarehub.com/tools/rescue/ or M-Flasher: https://github.com/jvitkauskas/m-flasher . If the FM1 application remains responsive, its USB-MIDI UBOOT soft key `F0 22 24 35 7D F7` requests the silicon's download mode, not a risky staged-loader rewrite. From download mode use a recovery tool that recognizes the actual flash ID and can **read a full backup first**, then install an authenticated stock V15/V16 or other compatible package. Do not attempt random sector writes or unsafe force-flashing. Not every fault is software-recoverable.

## Limits

This project does **not** contain real-FM1 runtime logs identifying which 1.8.3 rejection the user observed. The software-level defects above are actual code problems, not a definitive diagnosis of the physical unit. Host tests cannot prove USB-MIDI device re-enumeration, host matching, 1 MiB SPI hardware timing, power-loss safety, or successful V15/V16 physical boot. No firmware can promise arbitrary future chip variants or that arbitrary other custom firmware accepts all new flashchips.
